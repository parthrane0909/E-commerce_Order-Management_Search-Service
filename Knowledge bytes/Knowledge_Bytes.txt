Byte 1: What This Project Is — The Business Problem
Builds on: None — starting point
In plain terms:
This is a polyglot persistence e-commerce demo that demonstrates how different databases serve different purposes in a real-world order management system. It's not a production shop — it's a reference implementation showing how to properly separate concerns across MongoDB (catalog), PostgreSQL (orders), and Elasticsearch (search/analytics) with asynchronous synchronization via RabbitMQ and Celery.
Why it exists:
The project solves the problem of data ownership confusion in e-commerce systems. Most applications incorrectly use a single database for everything, leading to:
- Catalog changes corrupting historical order data
- Search performance degrading transactional writes
- No clear source of truth for financial records
This project demonstrates the correct pattern: each database owns exactly one domain, with a clear synchronization path for derived data.
The three user roles:
1. Customer — browses MongoDB catalog, adds to cart, places orders (PostgreSQL)
2. Admin — searches/analyzes orders in Elasticsearch dashboard, manages MongoDB catalog
3. System — Celery worker synchronizes PostgreSQL → Elasticsearch via RabbitMQ

Key architectural rules enforced:
Rule	Enforcement
MongoDB owns products only	Orders never read from MongoDB
PostgreSQL owns orders only	Orders never written to MongoDB/ES directly
Elasticsearch is read-only for orders	Admin search only; never source of truth
Sync is async, one-way	PostgreSQL → RabbitMQ → Celery → Elasticsearch
Order snapshots are immutable	OrderItems store title/price at purchase time

Byte 5: Database Responsibilities & Data Flow
Builds on: Byte 4
In plain terms:
Each database has a single, non-overlapping responsibility. The architecture prevents the most common e-commerce data bugs by enforcing ownership at the code level.
┌────────────────────────────────────────────────────────────────────────────┐
│                        DATABASE RESPONSIBILITY MATRIX                       │
├──────────────┬──────────────────────┬──────────────────┬──────────────────┤
│   Domain     │   MongoDB            │   PostgreSQL     │   Elasticsearch  │
├──────────────┼──────────────────────┼──────────────────┼──────────────────┤
│ Products     │ ✅ OWNER             │ ❌ Never reads   │ ❌ Never         │
│              │ - title, price       │   for products   │                  │
│              │ - category, tags     │                  │                  │
│              │ - variants, attrs    │                  │                  │
├──────────────┼──────────────────────┼──────────────────┼──────────────────┤
│ Orders       │ ❌ Never             │ ✅ OWNER         │ ❌ Never writes  │
│              │   writes orders      │ - users          │   (read-only for │
│              │                      │ - orders         │   admin search)  │
│              │                      │ - order_items    │                  │
│              │                      │ - snapshots      │                  │
├──────────────┼──────────────────────┼──────────────────┼──────────────────┤
│ Search/      │ ❌ Never             │ ❌ Never         │ ✅ OWNER         │
│ Analytics    │                      │                  │ - order search   │
│ (Admin)      │                      │                  │ - filters        │
│              │                      │                  │ - aggregations   │
└──────────────┴──────────────────────┴──────────────────┴──────────────────┘
Data Flow for Order Placement:
1. Customer clicks "Place Order" (frontend)
         │
         ▼
2. POST /api/orders {user_id, items[]}  ──► FastAPI
         │
         ▼
3. order_service.resolve_cart()
   - Fetch products from MongoDB by ID
   - Validate active, price > 0
   - Server-side pricing (client never trusted)
         │
         ▼
4. Explicit PostgreSQL transaction:
   BEGIN
   INSERT INTO orders ...
   INSERT INTO order_items ...  (snapshots title + price)
   COMMIT
         │
         ▼
5. sync_service.publish_order_sync() → RabbitMQ
         │
         ▼
6. Celery worker picks up task
   - Reads order from PostgreSQL
   - Builds ES document (snapshots!)
   - Indexes to Elasticsearch
   - Retries on failure
Critical Invariant: OrderItems store snapshots (title + price at purchase time). If MongoDB product changes later, historical orders remain unchanged.

Byte 7: Order Lifecycle — The Core Business Logic
Builds on: Byte 6
In plain terms:
Order creation is the most critical path. It must be correct, consistent, and auditable.
order_service.create_order(payload) — Step by Step:
def create_order(payload: OrderCreate) -> OrderCreateResponse:
    # 1. RESOLVE CART — Server-side validation & pricing
    lines, total = resolve_cart(payload.items)
    # - Fetch products from MongoDB by ID
    # - Validate active, price > 0
    # - Merge duplicate product_ids
    # - Server computes total (client total ignored)

    # 2. EXPLICIT POSTGRESQL TRANSACTION
    session = SessionLocal()
    try:
        session.begin()
        
        user = order_repo.get_user(session, payload.user_id)
        if not user: raise NotFoundError
        
        order = Order(
            order_number=_temporary_order_number(),  # TMP-...
            user=user,
            order_date=now,
            status="PENDING",
            total_amount=total,
        )
        session.add(order)
        session.flush()  # Get order.id
        
        order.order_number = f"ORD-{order.id:06d}"  # ORD-000042
        
        for line in lines:
            session.add(OrderItem(
                order=order,
                product_id=line.product_id,
                title=line.title,      # SNAPSHOT from MongoDB
                quantity=line.quantity,
                unit_price=line.unit_price,  # SNAPSHOT from MongoDB
            ))
        
        session.commit()  # ORDER IS NOW DURABLE
    finally:
        session.close()

    # 3. ASYNC SYNC — Only after COMMIT
    sync = sync_service.publish_order_sync(order.id, "order_created")
    return OrderCreateResponse(..., sync=sync)
Key Guarantees:
Guarantee	How It's Enforced
Server computes total	Client never sends total_amount
No partial orders	Explicit BEGIN/COMMIT/ROLLBACK
Snapshot isolation	OrderItem.title + unit_price copied at purchase
No lost orders on RabbitMQ failure	sync reported separately; order already committed
Idempotent ES indexing	_id = order_id makes reindex safe

     │                   │                   │
     ▼                   ▼                   ▼
  Can cancel       Can ship           Final state

def _build_filter(category=None, tags=None, q=None, visibility="active"):
    query = {}
    if visibility == "active": query["active"] = True
    if category: query["category"] = category.lower()
    if tags: query["tags"] = {"$all": [t.lower() for t in tags]}
    if q:
        pattern = {"$regex": re.escape(q), "$options": "i"}
        query["$or"] = [
            {"title": pattern},
            {"description": pattern},
            {"sku": pattern},
            {"tags": pattern},
        ]
    return query

Search Query (bool_prefix for prefix matching):
def build_search_query(request):
    filters = []
    should = []
    
    if request.status:
        filters.append({"terms": {"status": list(request.status)}})
    
    if request.query:
        should.append({
            "multi_match": {
                "query": request.query,
                "fields": ["customer.name^3", "customer.email", "order_number"],
                "type": "bool_prefix",  # <-- prefix matching!
                "operator": "or",
            }
        })
        should.append({
            "nested": {
                "path": "items",
                "score_mode": "max",
                "query": {
                    "multi_match": {
                        "query": request.query,
                        "fields": ["items.title^2"],
                        "type": "bool_prefix",
                        "operator": "or",
                    }
                }
            }
        })
    
    return {
        "query": {"bool": {"filter": filters, "should": should, "minimum_should_match": 1}},
        "aggs": {"revenue": {"sum": {"field": "total_amount"}}, "status_counts": {"terms": {"field": "status"}}},
        "sort": [{"order_date": "desc"}, {"order_id": "desc"}],
        "from": offset, "size": limit,
    }
Query Features:
Feature	Implementation
Full-text search	multi_match on customer + items
Prefix matching	type: "bool_prefix" on search_as_you_type fields
Status filter	terms query on status keyword
Date range	range on order_date
Price range	range on total_amount
Pagination	from / size
Sort	order_date desc, order_id desc
Revenue KPI	sum aggregation on total_amount
Status counts	terms aggregation on status
Byte 9: RabbitMQ + Celery — Async Synchronization
Builds on: Byte 8
In plain terms:
PostgreSQL commits the order, then asynchronously publishes a sync task. The Celery worker builds the Elasticsearch document from PostgreSQL (never MongoDB).
Flow:
POST /api/orders
    │
    ▼
PostgreSQL COMMIT (order durable)
    │
    ▼
sync_service.publish_order_sync(order_id, "order_created")
    │
    ▼
RabbitMQ queue: "orders_sync"
    │
    ▼
Celery Worker (concurrency=2)
    │
    ▼
sync_order_to_elasticsearch(order_id, reason="order_created")
    │
    ▼
1. SessionLocal() → SELECT order + items + user
2. build_order_document() → dict
3. ensure_index() → create index if missing
4. index_order_document(doc) → ES index
5. mark_search_indexed(order_id) → PostgreSQL bookkeeping

    result_serializer="json",
    accept_content=["json"],
    task_acks_late=True,        # Acknowledge AFTER processing
    worker_prefetch_multiplier=1,  # Fair distribution
)

Byte 12: Checkout & Cart
Builds on: Byte 11
In plain terms:
Cart is local-only (Pinia). Server re-validates and re-prices at checkout.
Cart State (cart.js):
state: () => ({
  items: {}  // { productId: { id, title, price, quantity, category } }
}),
getters: {
  itemCount: sum(qty),
  subtotal: sum(price * qty),
  isEmpty: items.length === 0,
},
actions: {
  add(product, qty=1) { /* merge or create, clamp 1-100 */ },
  setQuantity(id, qty) { /* clamp 1-100 */ },
  remove(id) { delete items[id] },
  clear() { items = {} },
}
Checkout Flow (CheckoutView.vue):
1. User clicks Cart → CartDrawer → "Checkout"
         │
         ▼
2. GET /api/products for each cart item (live prices)
         │
         ▼
3. Display line items with live prices
         │
         ▼
4. POST /api/orders { items: [{product_id, quantity}] }
         │           (no user_id — taken from JWT)
         ▼
5. order_service.create_order()
   - Validates all items still active
   - Re-prices from MongoDB
   - PostgreSQL transaction
         │
         ▼
6. On success: cart.clear(), show success panel with order number
Key Point: Cart prices are snapshots. At checkout, the server re-fetches live prices from MongoDB and re-computes total. The client total is never trusted.

How to diagnose the most common issues in this system.

Backend unhealthy	PG/Mongo/ES/Rabbit not ready	docker compose logs backend
